# Research: 20260714080036-restore-module-support

## Alternatives considered and rejected

1. **Port the old pre-refactor `parseModule` (inline/eager decode) as-is.**
   What: the v1 implementation (commit `3cf707c`, per `.spektacular/context.md:33-38`) decoded the module block immediately via `decodeBody`, then recursed into child files right away, tagging children with `meta.Module = moduleName`.
   Rejected: violates the hard constraint that module resources must be decoded through the DAG-ordered walk phase, not eagerly. The two-phase parse/decode split was deliberately introduced (`.spektacular/knowledge/decisions/parser-refactor-analysis.md`) specifically to fix interpolation-ordering bugs that inline decoding could not solve. Reintroducing eager decode would regress that fix for any module referencing not-yet-decoded siblings (e.g. `consul_1`'s `variables = { cpu_resources = resource.container.base.resources.cpu }`, which depends on a root resource that could be declared later in the file).

2. **Model a module as a special "container" vertex with an explicit parent/child graph structure in `dag.go`.**
   What: introduce a distinct vertex type or nested-graph construct so a module's children are structurally grouped under it in the DAG.
   Rejected: the DAG library (`internal/parser/dag.go:44-99`, using `github.com/jumppad-labs/dag` fork of `silas/dag`) has no concept of nested/grouped vertices — vertices are flat `any` resource instances. More importantly, this grouping already exists implicitly and correctly via the `Meta.Module` dot-joined string field + `FQRN.AppendParentModule` + `State.FindModuleResources` (see Chosen approach below) — building a parallel container-vertex abstraction would duplicate machinery that already works and violates the "prefer existing DAG/FQRN/Link infrastructure" technical-approach steer from the spec.

3. **Support remote/git module sources as part of this restoration (matching the old `parseModule` and the `TestParseModuleDoesNotCacheLocalFiles` fixture).**
   What: wire up `internal/getter/getter.go`'s `GoGetter.Get()` (already fully implemented, using `hashicorp/go-getter`, unused today) so `consul_3` in `modules/modules.xcl:41-45` (source `github.com/jumppad-labs/xcl/test_fixtures//single`) resolves via network fetch + cache under `p.options.ModuleCache`.
   Rejected: the spec's constraints explicitly restrict this work to local relative-path sources only ("remote or URL/git-based module sources are explicitly out of scope for this work"). **Conflict found during research**: the existing fixture `modules/modules.xcl` and test `TestParseModuleDoesNotCacheLocalFiles` (`internal/parser/parse_test.go:367-384`) both exercise a remote source and assert caching behavior for it. Per the spec's Success Metrics ("all currently-failing module-related parser tests pass"), this specific test cannot pass without remote-source support, which is explicitly out of scope. Resolved with the user during the architecture step: the fixture and test are edited to drop the remote-source assertion (see Out of Scope in plan.md).

4. **Use a separate lookup/registry keyed by module instance name for scoping, instead of `Meta.Module` + FQRN.**
   What: introduce a dedicated `ModuleInstance` tracking map outside the existing FQRN/State mechanism to keep module-scoped resources addressable.
   Rejected: `internal/resources/fqrn.go` already fully supports arbitrary-depth nested module scoping via a dot-joined `Module` string (confirmed by existing passing test `TestParseFQRNParsesComponents` parsing `"module.module1.module2.resource.container.mine..."` → `Module == "module1.module2"`), and `state.State.FindModuleResources`/`FindRelativeResource` (`state/state.go:89-175`) already provide instance-scoped and prefix-scoped queries. No new addressing mechanism is needed.

## Chosen approach — evidence

**Core insight: nearly all module infrastructure already exists and is wired for module-awareness; the gap is almost entirely the Phase-1 parsing stub plus a handful of commented-out propagation blocks.**

1. **Phase 1 gap — the actual bug.** `internal/parser/parser.go:332-339`:
   ```go
   case resources.TypeModule:
       // Module support is not yet implemented in v2
       continue
       //err := p.parseModule(file, b)
   ```
   This is the single point where module blocks are dropped. `parseResourcesInFile(file string, module string)` (parser.go:273) already takes a `module` parameter and passes it through to `parseResource(file, b, module)` (parser.go:345), which sets `rtMeta.Module = moduleName` (parser.go:494) — but every call site (`Parser.Parse`, parser.go:239) passes `""`, since nothing recurses into a module's own source directory. The fix is to build a `parseModule`-equivalent function that: (a) creates a `*resources.Module` shell via the same `parseResource`-style flow (so its own `variables`/`source`/`disabled` attributes get link-extracted and body-stored like any other resource — NOT decoded inline), (b) resolves `Source` as a local relative path against `filepath.Dir(file)`, (c) calls `findXclFiles` (util.go:20-53) on that resolved directory, and (d) recurses via `parseResourcesInFile(childFile, moduleInstanceName)` for each child file — reusing the exact same Phase-1 shell-creation path used for root resources, just with a non-empty module name. This directly satisfies the "must decode through DAG-ordered walk" constraint since nothing here calls `gohcl.DecodeBody`.

2. **FQRN nesting already works.** `internal/resources/fqrn.go:13-22` (`Module string` field, dot-joined), `fqrn.go:150-164` (`AppendParentModule`), confirmed by existing passing tests in `fqrn_test.go` (`TestParseFQRNParsesComponents`, `TestFQRNAppendsParentCorrectlyWhenExistingModule`). No changes needed here — nested modules (`module.disabled.sub.resource.container.enabled`) are already representable and parseable.

3. **Link/dependency extraction already recognizes modules.** `internal/parser/exp.go:140-146` (`processScopeTraversal`) already treats `module` as a valid traversal root alongside `resource`, `variable`, `output`. `internal/parser/util.go:493-568` (`getResourceDependencies`) already has a `fqdn.Type == resources.TypeModule` branch (line 518) that expands a bare `module.X` reference (e.g. `depends_on = ["module.consul_1"]`) to depend on every resource in that module via `rp.FindModuleResources(relFQDN.String(), true)` (line 528), and a general branch (lines 533-548) that resolves `module.X.output.Y`-style references via `rp.FindResource`. Every resource inside a module also automatically gets an implicit dependency edge on its own owning module vertex (util.go:550-565). **No changes needed** to `exp.go`, `getResourceDependencies`, or `dag.go` — once module shells exist in `parsedResources`/`State` with correct `Meta.Module`/`Meta.Links`, the DAG will already order and connect them correctly.

4. **`state.State` and `ConfigProvider`/`ResourceProvider` interfaces are already module-aware.** `dag.go:12-23` declares `FindRelativeResource`/`FindModuleResources` as required interface methods; `state/state.go:89-175` fully implements both (`FindRelativeResource` rewrites a path's module prefix relative to a parent; `FindModuleResources` filters by exact or prefix module-string match for `includeSubModules`). No changes needed.

5. **Disabled propagation needs completing, not inventing.** The propagation logic is already drafted as commented-out code:
   - `callbacks.go:75-90` — if a module resource evaluates as disabled, find all its resources via `FindModuleResources(rMeta.ID, true)` and `types.SetDisabled(d, true)` on each. This needs a live `ResourceProvider`/`rp` parameter threaded into `walkCallback` (currently the commented code references an undefined `c`), and it must run for the module vertex specifically, before/as its children are walked — since DAG order guarantees the module vertex is decoded before children (util.go:550-565 implicit edge), this propagation can safely run inside the module's own `walkCallback` invocation, setting `Disabled=true` on all current children ahead of their own decode step (each child's early disabled short-circuit at callbacks.go:39-46 will then correctly skip it).
   - The existing early-exit at `callbacks.go:39-46` (`if disabled { return early }`) already provides the "resource stays in state but isn't further processed" behavior the spec's resolved disabled semantics require (confirmed by passing test `TestParseDoesNotProcessDisabledResources`, parse_test.go:528-555) — this is exactly the mechanism needed for module-level disable, no new mechanism required.
   - Child-resource override (`disabled = !variable.enabled` in `single/container.xcl`) already works today for non-module resources via `processDisabled` (parser.go:705-734), which evaluates the `disabled` HCL expression **after** context build, so it naturally reads the resource's own already-resolved `variable.enabled` value. Since the module's disabled-propagation only pre-sets `Disabled=true` (an OR, never overriding a child's own `false`), and a child that's independently disabled via its own expression still gets caught by `processDisabled` regardless of module state, both directions of the override requirement fall out for free once propagation runs — confirmed against fixture `disabled/module.xcl` + `disabled/modules/resources.xcl`'s `disable_resources` variable pattern.

6. **Module variable-passing needs completing via `context.go`'s commented stub.** `context.go:103-122`: today, `if rMeta.Module != ""` the branch body is **entirely empty** (commented out) — meaning module-scoped resources currently get zero variable overrides beyond their own `Default` (already merged at context.go:52-57 from each `Variable` shell's own default). The needed logic: when building context for a resource inside a module, look up the owning `*resources.Module` shell (via the same `res.resources` map already used at context.go:42, keyed by the module's own FQRN `module.<name>`), read its (already-decoded, since DAG order guarantees module-before-children) variables field, and merge those values over `variableVars` before setting `ctx.Variables["variable"]`. Precedence per the spec's resolved requirements: module-instance-supplied value overrides the module's own variable default when present; falls back to the default otherwise — this is a simple two-layer merge (defaults, then supplied-if-present), analogous to the existing root-level `defaults < files < env < direct` chain at context.go:125 but scoped to just two layers for modules (no `.vars`-file/env layer applies inside modules, confirmed by `TestDoesNotLoadsVariablesFilesFromInsideModules`, parse_test.go:444-458, which the `else if options != nil` branch at context.go:123-138 already correctly gates to root-level only by being an `else` off `rMeta.Module != ""`).
   - `resources.Module.Variables` (module.go:19) is decoded from the module block's own `variables = { ... }` HCL attribute during the module vertex's own DAG-walk decode step — by the time a child resource needs it, it will already be a decoded value. **Update**: the field's original `any` type cannot actually be decoded by `gohcl.DecodeBody` at all (see Open assumptions #1 below) — this was a confirmed bug, not a shape ambiguity, and is resolved by retyping the field to `map[string]cty.Value`.
   - The unused `Module.SubContext *hcl.EvalContext` field (module.go:22-23, doc comment: "used to store the variables as a context that can be passed to child resources") appears to be exactly the intended mechanism for this — a natural implementation is to populate `SubContext` on the module resource during its own decode/walk step (building a `cty.ObjectVal` from its resolved `Variables`), then have `buildContextForResource` read `SubContext` off the owning module resource for children. This avoids re-deriving the merge logic per-child and matches the field's stated intent.

7. **Per-instance isolation ("does not cache/leak state between instances") is a natural consequence of correct FQRN scoping, not a separate mechanism.** Since each module instance (`consul_1`, `consul_2`, `consul_3`) gets its own `moduleName` passed through `parseResourcesInFile`, and each child resource's shell is a **freshly created** instance per recursion (not reused/cached across instances — `parseResource`'s `p.pluginRegistry.CreateResource`/`p.createBuiltinResource` calls, parser.go:368-480, always construct new objects), there is no shared mutable state between instances by construction, as long as the module-recursion logic calls the file-parsing/shell-creation path fresh for every instance (i.e., does NOT cache/reuse parsed shells across instances of the same source — this is the local-files half of `TestParseModuleDoesNotCacheLocalFiles`, parse_test.go:382-383: `require.NoDirExists(t, filepath.Join(p.options.ModuleCache, "single"))`, confirming local sources must be read fresh from disk every instantiation, never cached/materialized to a cache dir).

8. **No new dependencies needed.** go.mod (lines 5-21) already has `hashicorp/hcl/v2`, `path/filepath` (stdlib), and the `jumppad-labs/dag` fork — everything needed for local-path resolution, HCL parsing, and DAG walking is already present. `hashicorp/go-getter` and `internal/getter/getter.go`'s `GoGetter` exist but are explicitly NOT needed/used for the in-scope local-only work (see Alternative 3 above).

## Open assumptions

1. **`resources.Module.Variables any` decode shape — RESOLVED, no longer an assumption.** Verified directly against the vendored `gohcl`/`gocty` source (not assumed): `gohcl.decodeBodyToValue` (`gohcl/decode.go:102-131`) decodes a plain attribute field via `DecodeExpression(attr.Expr, ctx, fieldV.Addr().Interface())` → `gocty.ImpliedType(val)` (`gohcl/decode.go:294`); the project's `jumppad-labs/go-cty` fork's `ImpliedType` type switch (`cty/gocty/type_implied.go:30-73`) has no `case reflect.Interface` and falls through to `default: return cty.NilType, path.NewErrorf("no cty.Type for %s", rt)` for any `any`/`interface{}`-kind field. **Concrete finding: `Variables any` as currently declared cannot be decoded by `gohcl.DecodeBody` at all — it would error on every module block with a `variables = { ... }` attribute.** This is not implementation-time-only uncertainty; it's a confirmed bug requiring a fix now. Resolution: retype the field to `map[string]cty.Value` (or equivalent `cty.Value`-based shape) — see the plan's Data Structures section and Phase 2.1. Confirmed via repo-wide grep that no other code reads `resources.Module.Variables` today, so the retype is self-contained and does not ripple elsewhere. Does not affect the "State JSON shape must not change" constraint since `Module` is never part of `State`'s serialized shape.
2. **`consul_3`'s remote source in `modules/modules.xcl` and `TestParseModuleDoesNotCacheLocalFiles`. RESOLVED with user.** User confirmed (architecture-step pre-check): edit the fixture to replace `consul_3`'s remote source with a second local instance (or otherwise remove the remote-source usage from `modules.xcl`), and rewrite `TestParseModuleDoesNotCacheLocalFiles` to only assert local-source no-caching behavior (i.e. keep the `require.NoDirExists(t, filepath.Join(p.options.ModuleCache, "single"))` assertion, drop the remote-fetch/cache-exists assertion). This keeps the spec's "all currently-failing module-related tests pass" success metric achievable without implementing out-of-scope remote-source fetching. The plan's Phase 4.1 implements this fixture/test edit.
3. **Disabled-propagation ordering assumption — RESOLVED, confirmed true.** Traced directly through the `jumppad-labs/dag` walker source (`walk.go`): `walkVertex` (`walk.go:316-`) blocks on each dependency's `DoneCh` before calling `w.Callback(v)`, and every vertex's own `DoneCh` is only closed via `defer close(info.DoneCh)` after its own callback returns. Since `getResourceDependencies` (util.go:550-565) already adds an edge from every module-scoped resource to its owning module vertex, the walker's channel-wait mechanism structurally guarantees the module vertex's callback (and any disabled-propagation logic added to it) fully completes before any child's callback runs — even though the walker is concurrent/goroutine-based for independent subtrees, a single dependency edge is strictly honored. No further verification needed at implementation time.
4. **Module's own `Variables` attribute link-extraction — RESOLVED, confirmed true.** Read `exp.go:68-76` directly: `processExpr`'s `*hclsyntax.ObjectConsExpr` case recursively walks `v.ValueExpr` for every item in the object literal, which is exactly the shape of `variables = { cpu_resources = resource.container.base.resources.cpu }`. Combined with `getUniqueResourceLinks`/`getDependentResources` already walking all of a block's `b.Body.Attributes` (parser.go:601-625) generically regardless of block type, the module block's own `variables` attribute will have its embedded resource/variable references correctly extracted into `Links` with no extra code needed, as long as the module-parsing code (Phase 1.1) calls `getUniqueResourceLinks` on the module block exactly as `parseResource` already does for other block types.
