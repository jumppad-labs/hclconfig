## Overview

Applications built on XCL can now tear down everything XCL has created, and removing a block from the configuration now removes the real thing it described instead of silently forgetting it. Today a request to destroy reports success while doing nothing, and a removed block leaves its resource running with no record that it exists, so it can never be cleaned up. With this change, developers and their users get a teardown they can trust: resources are removed in an order that never pulls something out from under a resource that still depends on it, and anything that fails to be removed is kept on record so it can be retried.

## Requirements

- [x] **Destroy tears down everything in the saved state**
  A developer can ask the system to destroy everything it has created. The destroy works from the saved state, and needs no configuration.

- [x] **Destroy runs in the reverse of the create order**
  The system must destroy resources in the reverse of the dependency order it creates them in, so every resource that depends on a resource is destroyed before that resource.

- [x] **A failed destroy does not stop unrelated resources**
  When destroying a resource fails, the system still destroys every resource that isn't connected to the failed one, and reports the failure once it has done all it can.

- [x] **Failed destroys are kept for retry**
  A resource that fails to be destroyed must stay in the saved state, marked as failed to destroy, so a later destroy can try again.

- [x] **Destroyed resources leave the saved state**
  Every resource that is destroyed must be removed from the saved state. After a destroy that fully succeeds, nothing is left in the saved state.

- [x] **Progress is saved as the destroy goes**
  The system must save the state as each resource is destroyed, so an interrupted destroy resumes from where it stopped instead of starting over.

- [x] **Blocks without a provider are removed during a destroy**
  Variables, outputs, modules, disabled blocks and configuration-only types are removed from the saved state during a destroy.

- [x] **Removing a block from the configuration destroys its resource**
  When a resource that was created before is no longer in the configuration, applying the configuration must destroy that resource through its provider, not just drop it from the saved state.

- [x] **Removed resources are destroyed before anything is created or changed**
  Applying the configuration must destroy every removed resource, in the reverse of their dependency order, before creating or updating any resource.

- [x] **A failed removal stops the apply**
  If destroying a removed resource fails while applying, the system must stop before creating or updating anything. It keeps that resource in the saved state as failed to destroy and reports the failure, and the next apply retries the destroy first.

- [x] **Applying an empty configuration is an error**
  Applying a configuration that declares no blocks must fail with an error, without destroying, creating or changing anything. Destroy is the way to remove everything.

- [x] **Destroy is reported like every other step**
  Every destroy must be reported to the application the same way as creates and updates: a start and a success or failure for resources with a provider, and a success only for those without one.

- [x] **Destroying with nothing saved succeeds**
  Asking the system to destroy when nothing has ever been created must succeed and change nothing.

- [x] **The examples show the full cycle**
  The configuration-only example and the plugin example in the repository each apply the shared example configuration and then destroy it, ending with nothing in the saved state.

## Constraints

- Everything a destroy logs must be at debug level, except errors, which must be logged at error level. This applies to XCL's own messages and to how the repository's examples log destroy events.
- Resources without a provider must never be passed to one. Builtin blocks (variables, outputs, modules), disabled blocks and configuration-only types must not reach a provider during a destroy.
- A parent (a resource something depends on) must never be destroyed while any of its children (the resources that depend on it) still exists, including a child whose destroy failed.
- Each resource in the saved state must record its parents, the resources it depends on, so a destroy can be ordered from the saved state alone.

## Acceptance Criteria

- [x] **A full destroy calls every provider and empties the state**
  Given a configuration that has been applied, with resources handled by providers, destroying it succeeds. Every provider-handled resource receives exactly one destroy call, and the saved state afterwards contains no resources.

- [x] **Destroy needs no configuration**
  After an apply, with the configuration files deleted, destroy still succeeds and destroys every resource that was applied.

- [x] **Dependents are destroyed before what they depend on**
  Given a chain where C depends on B and B depends on A, the destroy calls arrive in the order C, B, A.

- [x] **A failed destroy leaves its dependencies in place**
  Given C depends on B, B depends on A, and an unrelated resource D, when destroying B fails: C and D are destroyed, A receives no destroy call, the destroy returns an error naming B, and the saved state contains B and A only.

- [x] **A failed resource is marked and can be retried**
  After a destroy in which B failed, B is in the saved state marked as failed to destroy. A second destroy, where B now succeeds, destroys B and then A and leaves the state empty.

- [x] **An interrupted destroy resumes**
  If the process stops partway through a destroy, the saved state holds exactly the resources not yet destroyed, and a second destroy calls providers only for those resources.

- [x] **No provider is called for blocks without one**
  Destroying a configuration made only of variables, outputs, modules, a disabled block and configuration-only types succeeds, calls no provider, and leaves the saved state empty.

- [x] **Removing a block destroys its resource on the next apply**
  Given resources X and Y were applied, when X is removed from the configuration and it is applied again, X's provider receives a destroy call, X is not in the saved state, and Y is unchanged.

- [x] **Removed resources are destroyed before creates and updates**
  Given an apply that both removes resource X and adds a new resource Z, X's destroy call happens before Z's create call.

- [x] **Removed resources are destroyed in reverse order**
  Given removed resources where Q depends on P, both removed in one apply, Q is destroyed before P.

- [x] **A failed removal stops the apply**
  When destroying a removed resource X fails during an apply that also adds Z: the apply returns an error naming X, Z is never created, and X is in the saved state marked as failed to destroy. The next apply, with X's destroy now succeeding, destroys X and then creates Z.

- [x] **Destroy events are reported**
  With an event handler registered, destroying a provider-handled resource reports a destroy start followed by a success, and a failing one reports a start followed by an error. Destroying a variable reports only a success.

- [x] **An empty configuration is rejected**
  Applying a configuration directory that contains no blocks returns an error, calls no provider, and leaves the saved state unchanged.

- [x] **Order comes from the saved state**
  After an apply, with the configuration files deleted, a destroy of a chain where C depends on B and B depends on A still destroys in the order C, B, A.

- [x] **Both examples apply and destroy**
  Running the configuration-only example and the plugin example each applies the shared configuration, then destroys it, and ends with an empty saved state. Both run as part of the normal test suite.

- [x] **Destroy with nothing saved**
  Destroying when nothing has been applied (no saved state) succeeds, calls no provider, and creates no saved state.

## Technical Approach

- Destroy walks the same dependency graph as create, backwards, rather than building a separate ordering for destroy.
- Build on the per-resource destroy handling that already exists but is not connected: it calls the provider, reports destroy events, and skips resources without a provider. Prefer reusing it over writing a second one.
- Report destroys through the existing event handler, alongside parse and create events, rather than a new reporting mechanism.
- Accepted trade-off of destroying removed resources first: what a removed resource provided is briefly missing before its replacement exists, in exchange for freeing names and ports the new resource may need.

## Success Metrics

- Nothing is orphaned: for every resource a provider created, either a destroy removes it, or the saved state still holds it as failed to destroy. Nothing a provider created ends up both still in existence and missing from the saved state. The normal test suite checks this for both destroy and removing a block.
- A parent is never destroyed after a child fails: in every destroy, and in every apply that removes blocks, no resource receives a destroy call once destroying something that depends on it has failed. The normal test suite checks this for both destroy and removing a block.
- No regression: the full test suite and vet checks pass, with apply behaviour unchanged for configurations that remove nothing.

## Non-Goals

- Targeted destroy: destroying only some resources, such as one resource and its children, is out of scope. Destroy always covers everything in the saved state.
- Create-before-destroy: creating a replacement before removing the old resource is out of scope.
- Destroying only what a given configuration declares: passing a configuration to destroy, to limit it to what that configuration declares, is out of scope. Destroy takes no configuration and removes everything in the saved state.
- Replacing a resource whose settings changed: changed resources keep today's update behaviour. Automatically destroying and recreating them is out of scope.
- State locking: preventing two applies or destroys from running against the same saved state at once is out of scope.
