# Destroy cycle

`Config.Destroy` now tears down everything that was applied, working only from the saved state, and destroys dependents before the things they depend on. Removing a block from the configuration now destroys the real resource on the next apply, instead of silently forgetting it. Anything that fails to be destroyed stays in the saved state for a retry. An interrupted destroy picks up where it stopped. Applying an empty configuration, or loading state that holds unregistered types, now fails instead of silently losing track of resources.

> Derived from project xclconfig (file), spec/plan 20260919152915-destroy-cycle. See the project-level record for the full feature.

## What changed in this repo

- **Public API** (`config.go`, `events.go`, `options.go`):
  - `Config.Destroy()` loads the saved state, or uses the in-memory state when no store is configured, and destroys everything in it.
  - It returns nil without writing anything when nothing was saved.
  - Load failures are wrapped as `failed to load state: …`.
  - `Config.Apply` passes on the new `xcl.ErrEmptyConfiguration`.
  - The event handler docs now cover Destroy.
- **Parser** (`internal/parser`):
  - A new `destroyer` (`destroy.go`) walks a set of resources children-first and saves the working state after each one. It removes destroyed resources and marks failed ones `destroy_failed`.
  - `destroyWalkCallback` reports each outcome to the destroyer and also skips disabled blocks.
  - `buildDestroyDAG` is built from `Meta.Parents`.
  - `buildCreateDAG` records those parents.
  - The new `Parser.Destroy(saved)`.
  - `Parser.Apply` now:
    - rejects an empty configuration (`ErrEmptyConfiguration` in `errors.go`);
    - destroys removed resources before the create walk;
    - stops, returning the partial state, if a removal fails.
- **Types** (`types/resource.go`): `Meta.Parents []string` (`json:"parents,omitempty"`), which is internal and can't be set from HCL.
- **State** (`state/`): `FileStateStore.Load` returns the new `UnknownTypesError` (sorted, unique types) instead of dropping entries it can't create.
- **Examples** (`example/configonly`, `example/plugin`):
  - `run` takes a state path, uses a file state store, applies, prints, then destroys.
  - `main` keeps its state in a temporary directory.
- **Docs**: `docs/parser-lifecycle.md`, `docs/state.md`, `docs/overview.md`, `docs/plugin-developer-guide.md`, `docs/plugins.md`, `docs/README.md` and `README.md` describe Destroy, removal, recorded parents and the new errors.
- **Tests and fixtures**:
  - `internal/parser/{parents,destroy,removal}_test.go`
  - `config_destroy_test.go`
  - new Load tests in `state/file_state_store_test.go`
  - the example tests
  - fixtures under `internal/test_fixtures/config/lifecycle/{module_reference,disabled,removal}` and `config/empty`
  - the golden schema `internal/schema/test_fixtures/embedded.go` updated for `Parents`
  - the old commented-out `Parser.Destroy` tests removed

**Breaking changes:**
- `FileStateStore.Load` errors on unregistered types.
- Applying an empty configuration errors.
- Removed blocks are destroyed through their provider.
- `destroyed` is never saved.

## Why

XCL is the library that owns the lifecycle, so it is where destroy has to live. Before this change, `Config.Destroy` reported success while doing nothing, and a removed block left its real resource running with nothing recording that it existed. Recording each resource's parents in the saved state is what lets a destroy be ordered without any configuration. Saving after every resource is what makes an interrupted destroy resumable.
