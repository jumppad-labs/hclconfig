# Destroy cycle

## What was built

Applications built on XCL can now tear down everything XCL created. When a block is removed from the configuration, the next apply destroys the real resource behind it; before this change the resource was forgotten while it kept running.

- **Config.Destroy is real.** It was a stub that returned success and did nothing. Now it works from the saved state alone, with no configuration paths, and destroys every resource through its provider, dependents before the things they depend on. The saved state is written after every resource. A destroy that is interrupted therefore resumes where it stopped.
- **Destroy failures.** A resource whose destroy fails stays in the saved state as `destroy_failed`, together with everything it depends on. Unrelated resources are still destroyed. The error names every failure, and running Destroy again retries them.
- **Blocks without a provider.** Variables, outputs, modules, disabled blocks and configuration-only (registered) types never reach a provider. They fire a `destroy` success event and leave the state.
- **Destroying with nothing saved.** Destroy succeeds and writes nothing.
- **Recorded parents.** Every saved resource now records its parents in `meta.parents`: the resolved IDs of the resources it depends on, covering explicit `depends_on`, references, module-wide references and the module the resource sits in. The destroy graph is built from these alone and walked in reverse, so destroy order always mirrors create order.
- **Removal during Apply.** Apply now destroys resources that were applied before but are no longer in the configuration, children first, before anything is created or changed. If one of those destroys fails, Apply stops before creating or changing anything. It keeps the resource as `destroy_failed`, and the next apply retries it first. Applies that remove nothing behave exactly as before.
- **Empty configuration.** Applying a configuration that declares no blocks now fails with `xcl.ErrEmptyConfiguration` and touches nothing. Destroy is the way to remove everything.
- **Unknown types in saved state.** `FileStateStore.Load` fails with `state.UnknownTypesError`, which names every saved type the registry can't create. It no longer silently drops those entries, which a later save would have erased from the state for good.
- **Events and logging.** Destroy events flow through `xcl.WithEventHandler` like create and update events. Provider resources report start, then success or error. Nothing in the destroy path logs above debug unless something fails.
- **Examples.** The configuration-only and plugin examples now keep their state in a file. They apply the shared configuration, print it, then destroy it and end with an empty saved state. Their tests check the providers' destroy logging and the event phases.
- **Documentation.** The lifecycle, state, overview and plugin-developer guides and the README describe all of the above. The README adds a "State and Destroy" section.

**Breaking changes:**
- Loading saved state that holds unregistered types now errors. Register every type or plugin before loading.
- Applying an empty configuration now errors.
- Removed blocks are now destroyed through their provider.
- `destroyed` is never saved, because destroyed resources leave the state.

## Why it matters

Before this change, a request to destroy reported success while doing nothing. A removed block left its resource running with nothing recording that it existed, so it could never be cleaned up. Developers and their users now get a teardown they can trust. Nothing is pulled out from under a resource that still depends on it, and anything that fails to be removed stays on record for a retry. Nothing a provider created can end up both still running and missing from the saved state.

## Deviations from the plan

- `buildCreateDAG` connects a resource to the root when none of its dependencies resolved, rather than when it has no dependencies at all. This avoids an unconnected vertex.
- Variable references count as parents. For example, a network that references a variable lists `variable.<name>` as a parent.
- Adding `Meta.Parents` meant updating the golden schema `internal/schema/test_fixtures/embedded.go`.
- `ErrEmptyConfiguration` lives in `internal/parser/errors.go` and is re-exported as `xcl.ErrEmptyConfiguration`, because applications can't import the internal parser package.
- The event-handler docs in `events.go` and `options.go` now cover Destroy too. The lifecycle doc's out-of-date claim that Config had no way to set an event handler was corrected.
- New test fixtures were added:
  - `lifecycle/module_reference`: a module-wide `depends_on`.
  - `lifecycle/disabled`: a disabled provider block.
  - `lifecycle/removal/*`.
  - `config/empty`.
- The resume tests restart a destroy from every real per-resource snapshot, not just one.
- The removal test compares a kept resource's saved entry without `meta.file`, `meta.line` and `meta.column`, which change legitimately when the fixture file changes.
